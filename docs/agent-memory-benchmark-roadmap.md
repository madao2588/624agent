# Agent Memory Leaderboard 应试系统：重点、难点与开发路线

> 更新日期：2026-09-01
>
> 项目：AML Memory Candidate / `624agent`
>
> 目标路线：Academic Methods · Textual Memory · 公开代码 · 平台部署

## 1. 一句话结论

当前 V1 已经是一套可靠、可复现、符合 Add/Search 基本契约的词法检索基线；下一阶段的核心不是让 Search 直接回答问题，而是把它升级为一套由 `gpt-4o-mini` 辅助理解、能够处理语义、关系、时间、更新、偏好和规则，同时始终返回原始证据的长期记忆系统。

```text
当前：可靠地保存与按词检索
目标：理解记忆 → 组织记忆 → 组合证据 → 返回可审计的原始证据
```

## 2. 评测边界：系统究竟负责什么

Agent Memory Leaderboard 把参赛方与平台的职责明确分开：

```text
参赛系统                                         评测平台
┌──────────────────────────────┐                 ┌────────────────────┐
│ Add：接收、理解、组织和写入记忆 │                 │ Answer：统一生成答案 │
│ Search：检索并排序原始记忆证据   │ ── evidence ─▶ │ Score：统一完成评分  │
└──────────────────────────────┘                 └────────────────────┘
```

必须坚持的边界：

- Add 返回 HTTP 200 前，记忆必须已经持久化并可立即搜索。
- Search 只返回记忆证据，不直接生成最终答案，也不把答案伪装成记忆。
- `user_id` 是唯一检索隔离边界；`session_id` 只能用于组织记忆。
- 正式评测按参赛系统返回顺序最多读取 Top 100。
- 参赛系统 Add/Search 内使用的生成式模型必须是 `gpt-4o-mini`。
- 平台不限定数据库、索引、Embedding 模型或内部架构。
- 原始消息必须保留，所有摘要、事实、关系和状态只能作为检索辅助。

官方依据：

- [Agent Memory Leaderboard 文档](https://agentmemoryleaderboard.ai/docs)
- [Add / Search API 指南](https://agentmemoryleaderboard.ai/api-guide)

## 3. 当前基线已经完成什么

当前实现的价值主要在“工程可靠性”和“接口合规性”，而不是复杂记忆能力。

| 已完成能力 | 当前实现 | 意义 |
| --- | --- | --- |
| 同步 Add | SQLite 事务写入原始消息和 FTS5 | 成功返回后可以立即 Search |
| 请求幂等 | `request_id` + 规范化负载哈希 | 重试不产生重复记忆，冲突请求返回 409 |
| 用户隔离 | 候选检索和原文回表均限制 `user_id` | 防止不同评测样本或用户串号 |
| 词法检索 | FTS5 + BM25 | 对原词、专有名词和明确事实有效 |
| 上下文补充 | 同用户、同会话相邻消息扩展 | 避免只返回孤立句子 |
| 证据可审计 | 最终返回原始消息 | 不生成或篡改评测答案 |
| 可复现交付 | Docker、测试、预检、CI | 平台可以按公开仓库构建和运行 |

当前边界：

- 还没有语义 Embedding 和向量检索。
- 还没有 LLM 记忆抽取、查询理解或重排。
- 还没有实体关系图、多跳组合和事件链。
- 还没有事实更新、矛盾处理和“当前状态”视图。
- 还没有隐含偏好、规则、流程和经验记忆。
- 还没有面向公开数据集的离线检索回归体系。

因此，V1 可以证明“服务能被评测”，但不能证明“记忆能力有竞争力”。

### 4.2 数据集解读

#### LoCoMo-Refined

- 基于超长、多会话对话提问。
- 重点考察时间、事件、人物关系和偏好。
- 更严格地区分“话题相关”和“细节正确”；时间粒度错误、遗漏必要事实、添加无依据内容都会失败。
- 对系统的要求：精确证据、时间结构、多条证据覆盖和低噪声排序。

来源：[LoCoMo-Refined](https://github.com/mem-eval-suite/LoCoMo_refined)

#### ScriptMem

- 基于真实剧本叙事构造人物、事件和关系图。
- 包括单选、复选和排序题。
- 六类问题覆盖用户画像、事件追踪、时间演化、社会关系、细粒度数据和经验总结。
- 对系统的要求：实体归一化、关系图、多跳路径、事件顺序以及精确的证据集合。

来源：[ScriptMem](https://github.com/memorax-ai/ScriptMem)

#### LongMemEval-Refined 与 LongMemEval-S

- 共同覆盖信息提取、多会话推理、知识更新、时间推理和信息不足时的克制。
- LongMemEval-S 每个问题包含约 115k tokens、约 40 个历史会话；证据可能散落在多个非相邻会话中。
- `knowledge-update` 要求系统区分旧事实和最新事实。
- `abstention` 要求证据不存在时不要检索出看似相关但错误的内容。
- 对系统的要求：语义召回、时间索引、状态更新、多证据召回和负证据意识。

来源：[LongMemEval](https://github.com/xiaowu0162/LongMemEval)

#### CLBench

- 考察模型能否从上下文中学习此前未知的知识、规则、流程和经验规律。
- 覆盖领域知识推理、规则系统应用、复杂流程执行、经验发现与模拟。
- 不是简单找一句答案，而是要找齐约束、例外、步骤和条件。
- 对系统的要求：规则记忆、过程记忆、结构化步骤、条件检索和完整证据覆盖。

来源：[CLBench](https://github.com/Tencent-Hunyuan/CL-bench)

#### PersonaMem-v2

- 包含大量用户画像、偏好和现实场景。
- 重点是从长对话中推断没有被直接声明的隐含偏好。
- 对系统的要求：跨会话聚合偏好信号、区分稳定偏好和临时表达，并保留形成推断的来源。

来源：[PersonaMem-v2](https://github.com/bowen-upenn/PersonaMem-v2)

#### BEAM

- 对话规模从 128K 延伸到 10M tokens。
- 同时考察信息提取、矛盾解决、事件排序、知识更新、多会话推理、偏好、指令、摘要、时间和克制。
- 对系统的要求：分层记忆、压缩与保真并存、可扩展索引、多路召回和有限成本下的检索规划。

来源：[BEAM](https://github.com/mohammadtavakoli78/BEAM)

## 5. 这次任务的重点

### 重点一：从“关键词命中”升级为“语义证据召回”

正式问题是自然语言，不会保证与原文共享关键词，也不会保证使用冒号或固定模板。

例子：

```text
记忆：我最近把早餐里的牛奶换成了燕麦饮，因为乳糖不耐受。
问题：用户为什么开始选择植物奶？
```

只依靠 FTS5 可能没有共同词；语义向量和查询理解才能建立“燕麦饮—植物奶”“乳糖不耐受—选择原因”的联系。

### 重点二：LLM 只增强记忆过程，不能越权回答

`gpt-4o-mini` 可以用于：

- Add 阶段抽取事实、实体、关系、事件、时间、偏好、规则和状态变化；
- Search 阶段识别问题意图、拆解多跳需求、生成受限查询和重排候选；
- 判断候选证据是否覆盖问题需要的关系或时间范围。

但它不能：

- 把推测或最终答案直接写进 Search 响应；
- 生成没有原始消息来源的“证据”；
- 使用评测答案、标签或泄漏数据规划检索。

### 重点三：结构化辅助记忆与原始证据双轨并存

结构化记忆用于提高检索能力，原始消息用于最终审计。

```text
辅助层：事实 / 实体 / 关系 / 事件 / 状态 / 偏好 / 规则 / 向量
                         │ provenance
                         ▼
证据层：不可改写的原始消息 + user_id + session_id + timestamp
```

任何辅助记录都必须保存 `source_message_id`，最终结果必须回到原始消息。

### 重点四：基准驱动，但不能对题库硬编码

开发可以借助公开数据集建立能力回归，却不能存储题目答案、利用问题标签进行特殊路由或重建私有评测集。正确的做法是把基准暴露出的能力抽象成通用机制。

## 6. 核心难点

### 难点 1：语义召回与精确召回的平衡

- 向量检索能找到同义表达，但可能引入“语义相似却事实错误”的结果。
- BM25 对姓名、日期、编号和专有名词更可靠，但容易漏掉改写问题。
- 解决方向：BM25 与 Dense 独立召回，通过 RRF 融合，再进行有界重排。

### 难点 2：多跳证据不是单条相似文本

问题可能需要先找到人物，再找到该人物参与的事件，最后找到事件的结果。单次相似度排序无法保证链条完整。

- 建立实体和关系索引；
- 将问题拆成有限的证据需求；
- 对第一轮命中的实体做有界扩展；
- 以来源覆盖和链条完整性重排，而不是无限 Agent 循环。

### 难点 3：时间、更新与矛盾治理

记忆中可能同时存在：

```text
8 月 20 日：会议定在周三下午。
8 月 26 日：会议改到周四上午。
```

两条都是历史证据，但“当前安排”只能由最新有效状态回答。系统需要区分：

- 事件发生时间与写入时间；
- 旧状态、当前状态和已撤销状态；
- 真正矛盾与自然更新；
- 精确时间和模糊时间。

### 难点 4：隐含偏好不能脱离证据自由推断

PersonaMem 类任务要求跨多次行为推断偏好，但一次偶然选择不应立刻变成稳定画像。需要保存：

- 偏好主题和取值；
- 明示或隐含；
- 支持次数、最近时间和置信度；
- 正反证据及来源。

### 难点 5：规则和流程必须完整召回

CLBench 的失败往往不是完全没找到，而是漏掉一个条件、例外或步骤。系统需要把规则表示为：

```text
适用范围 + 前置条件 + 步骤顺序 + 例外 + 输出要求 + 来源
```

检索排序需要奖励“规则覆盖完整”，而不只是单条文本相似。

### 难点 6：证据不足时保持克制

Search 不负责生成“我不知道”，但它必须避免用低相关结果填满 Top K。需要：

- 绝对相关性门槛；
- 结果置信度和候选间差距；
- 多路检索都未命中时允许返回空数组；
- 不把选项本身伪造成证据。

### 难点 7：超长规模下的成本、延迟和稳定性

- 不能把所有历史交给 LLM 重新阅读。
- Add 必须同步完成，模型调用失败策略必须明确。
- Search 要支持并发，并在有限延迟内完成多路召回。
- 所有缓存和索引仍需以 `user_id` 隔离。

## 7. 目标架构

### 7.1 Add：一次写入，多种可检索视图

```text
Add 请求
   │
   ├─ ① 契约校验、幂等检查、user_id 隔离
   │
   ├─ ② 保存不可改写的原始消息
   │
   ├─ ③ gpt-4o-mini 结构化抽取
   │      ├─ facts / entities / relations
   │      ├─ events / temporal expressions
   │      ├─ preferences / persona signals
   │      ├─ rules / procedures
   │      └─ updates / contradictions
   │
   ├─ ④ 建立 BM25、向量、关系、时间和状态索引
   │
   └─ ⑤ 同一事务或明确补偿后确认全部可搜索，再返回 HTTP 200
```

### 7.2 Search：理解问题，多路找证据，最终回到原文

```text
自然语言问题
   │
   ▼
gpt-4o-mini 查询规划
   ├─ 识别事实 / 多跳 / 时间 / 偏好 / 规则 / 克制意图
   └─ 生成有限、可审计的检索子查询
   │
   ├────────────┬────────────┬────────────┬─────────────┐
   ▼            ▼            ▼            ▼             ▼
BM25         Vector       Relation      Temporal      State/Rule
   └────────────┴────────────┴────────────┴─────────────┘
                           │
                           ▼
                    RRF 融合 + 去重
                           │
                           ▼
              覆盖度 / 时间 / 多样性有界重排
                           │
                           ▼
             回表读取原始消息，按顺序返回 Top 100
```

### 7.3 建议的数据层

| 层 | 主要数据 | 作用 |
| --- | --- | --- |
| Source | 原始消息、角色、时间、用户、会话 | 唯一可返回的事实证据 |
| Semantic | Embedding、关键词、主题 | 改写和同义问题召回 |
| Graph | 实体、关系、事件参与者、来源边 | 多跳和关系查询 |
| Temporal | 事件时间、有效区间、先后关系 | 时间推理和事件排序 |
| State | 事实版本、当前值、替代/撤销关系 | 知识更新和矛盾治理 |
| Persona | 偏好、证据次数、置信度、正反来源 | 个性化与隐含画像 |
| Procedure | 条件、步骤、例外、输出要求 | 规则与流程执行 |

## 8. 主要开发步骤

### 阶段 0：冻结可靠基线

目标：保证增加模型和索引后不破坏已有契约。

主要任务：

1. 保留现有 Add/Search 黑盒预检和用户隔离测试。
2. 增加检索组件协议测试，锁定最终只回原始消息。
3. 固定可复现的基线配置与运行记录。

验收：原有静态检查、测试、Docker 和预检全部通过；增强功能关闭时行为与 V1 一致。

### 阶段 1：模型与语义基础设施

目标：引入合规、可替换、可观测的模型能力。

主要任务：

1. 实现 OpenAI-compatible 客户端，生成式模型锁定 `gpt-4o-mini`。
2. 增加 Embedding 适配器和持久化向量表。
3. 增加超时、重试、并发限制、调用计数和脱敏日志。
4. 明确模型失败时是整次 Add 失败，还是使用经过披露的降级模式。

验收：相同固定输入得到结构稳定的 JSON；密钥不进入日志或仓库；Add 返回前向量可搜索。

### 阶段 2：结构化记忆写入

目标：从原始消息生成可追溯的多视图记忆。

主要任务：

1. 定义事实、实体、关系、事件、时间、偏好、规则和状态 schema。
2. 设计严格 JSON Schema 提示词并校验模型输出。
3. 每条辅助记录绑定 `user_id` 和一个或多个 `source_message_id`。
4. 实现实体归一化、时间标准化和重复事实合并。

验收：任何辅助记录都能追溯到原文；无来源内容不能进入可检索索引；跨用户写入不可发生。

### 阶段 3：混合检索与重排

目标：解决自然语言改写、专有名词和候选排序问题。

主要任务：

1. BM25 与向量检索分别产生候选。
2. 使用 RRF 融合，避免直接比较不同量纲的分数。
3. 增加 MMR 或来源多样性，避免 Top K 被同一局部重复片段占满。
4. 使用 `gpt-4o-mini` 或确定性特征对有限候选重排。
5. 最终统一回表读取原始消息。

验收：公开改写样本的 Recall@K 明显优于词法基线；姓名、日期和编号不因向量召回而退化；顺序稳定。

### 阶段 4：时间、更新、关系与规则治理

目标：覆盖最难的多跳、更新、偏好和流程题。

主要任务：

1. 建立实体—关系—事件图，支持有界一跳/二跳扩展。
2. 建立事实版本和当前状态视图。
3. 建立事件时间线和先后关系。
4. 建立偏好证据累计与反证更新。
5. 建立规则/流程的条件、步骤和例外结构。
6. 增加绝对相关性门槛和空结果策略。

验收：更新问题优先召回新状态且保留旧证据；多跳问题覆盖所有必要来源；无答案问题不会被低相关结果污染。

### 阶段 5：公开基准回归与消融

目标：用公开数据验证通用能力，而不是凭直觉堆功能。

主要任务：

1. 建立不包含答案泄漏的公开数据适配器。
2. 记录 Retrieval Recall@K、MRR/NDCG、必要证据覆盖率、延迟和成本。
3. 分别运行 lexical、dense、hybrid、graph、temporal、rerank 消融。
4. 按数据集失败类型建立回归案例。

验收：每个新增机制都有可复现增益或明确被删除；报告区分检索指标和平台最终回答指标。

### 阶段 6：提交冻结与正式运行准备

目标：形成平台可以复现的固定参评版本。

主要任务：

1. 锁定依赖、模型、提示词、Embedding、配置和 Docker 镜像。
2. 完成并发、超时、重试、磁盘增长、重启恢复和 30 天数据清理测试。
3. README 披露引用、方法变化、运行成本和已知限制。
4. 跑完整静态检查、测试、Docker、黑盒预检和公开数据回归。
5. 固定 Git commit 后再申请正式评测。

验收：平台按文档可复现启动；正式配置不依赖本机文件；所有密钥由环境变量提供；检索结果始终为原始证据。

## 9. 推荐依赖顺序

```text
可靠契约
   ↓
模型适配 + Embedding
   ↓
结构化写入
   ↓
混合检索
   ↓
时间 / 状态 / 图 / 规则
   ↓
公开基准回归与消融
   ↓
固定版本并提交
```

不能颠倒的原因：

- 没有来源绑定，图和摘要会失去审计能力。
- 没有混合检索基线，无法判断图或 LLM 重排是否真的带来增益。
- 没有失败分类和消融，系统会变成成本高但不可解释的功能堆叠。
- 没有版本冻结，平台复现结果可能与本地结果不一致。

## 10. 风险与控制措施

| 风险 | 典型后果 | 控制措施 |
| --- | --- | --- |
| LLM 抽取幻觉 | 不存在的事实进入索引 | 严格 JSON Schema、来源 ID 必填、最终只回原文 |
| 向量过度召回 | 相关但错误的证据挤入前排 | BM25 混合、门槛、时间/实体校验、有界重排 |
| 旧事实污染 | 更新后仍优先返回旧安排 | 事实版本、当前状态、替代边、时间排序 |
| 多跳无限扩展 | 延迟和成本不可控 | 最多两跳、候选预算、固定调用次数 |
| 用户串号 | 严重隐私与资格问题 | 每张表、缓存、索引和回表路径都包含 `user_id` |
| Add 模型超时 | 无法满足同步写入 | 并发限制、重试预算、明确失败语义、容量测试 |
| 评测泄漏 | 取消资格 | 禁止答案/标签输入检索，公开数据仅用于能力回归 |
| 结果难以复现 | 平台复核失败 | 锁定模型和提示词，保存非敏感配置与方法版本 |

## 11. 最近一轮建议实施清单

第一轮增强应控制范围，只完成语义地基：

1. 新增 `ModelClient` 和 `Embedder` 协议。
2. 接入 `gpt-4o-mini` 的严格结构化输出。
3. 新增持久化向量表与来源绑定。
4. 实现 Dense Retriever。
5. 实现 BM25 + Dense RRF。
6. 增加改写、专有名词、用户隔离和原文回表回归测试。
7. 在本地公开样本上比较 lexical 与 hybrid。
8. 只有在混合检索得到可复现增益后，再进入关系图和时间治理。

这一步完成后的系统仍不会直接答题，但会从“只能按词找”升级为“能够理解问题并召回可靠原始证据”。

## 12. 完成定义

冲榜候选版本只有同时满足以下条件，才算真正准备完成：

- 接口、同步性、幂等、隔离、鉴权和 Top K 契约全部通过。
- 所有 LLM 生成式调用符合 `gpt-4o-mini` 要求。
- 自然语言改写、多跳、时间、更新、偏好、规则和无答案都有回归覆盖。
- 每条结构化记忆都能追溯到原始消息。
- Search 永远只返回原始证据，不返回生成答案。
- 公开数据回归、消融、延迟、成本和失败类型均有记录。
- Docker 从干净环境可复现构建、启动、重启和运行。
- 固定提交版本与评测版本完全一致。
- README 完整披露引用、模型、架构、运行方法与已知限制。
